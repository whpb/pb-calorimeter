# File structure
- The program will be run from main.py, which should contain only logic. Functions live in functions/.
- `force_run.py` is a fourth entry point, launched only by `app.py`'s "Run an Experiment": it takes the stop sentinel as `argv[1]` and the operator's experiment name as `argv[2]`, records immediately and stops when the interface asks, never consulting `UserInput` at all. Unlike testing mode it *does* run `analyse_samples`, because a forced run is attended by definition — someone had to press Stop.
- So the three recording paths differ only in when they stop and whether anyone is present: testing mode stops at User Value 1 and reports nothing; force run stops at the interface and reports; re-analysis has no rig at all and reports.
- `app.py` is the operator-facing front end and the third entry point (`App.bat`): a Tk menu with the branding, a name screen, a holding screen, and a results panel. It is a **launcher, not a host** — it never imports the measurement, it runs `main.py`, `force_run.py` or `reanalyse.py` as a child process. That is deliberate: `main.py` blocks on its poll loop and `select_windows` calls `plt.show()`, which starts its own Tk mainloop, so hosting either inside the menu's mainloop would mean two event loops fighting. Separate processes keep every existing function untouched and isolate a crash to the child.
- `reanalyse.py` is a second entry point, same rule: logic only. It re-runs the analysis half against a results CSV that already exists, so a badly cut baseline can be re-cut without repeating the experiment. `Reanalyse.bat` launches it; a CSV dragged onto the .bat arrives as `argv[1]`, and double-clicking it opens a file dialog instead (`choose_results_file`).

- The interface is drawn, not themed. `functions/tokens.py` is the design system — every colour, font, spacing step and grid measure in one module, no functions — and the primitives are one-function-per-file like everything else: `build_card`, `build_button`, `build_badge` and `build_field` are images composited with PIL and placed on a `tk.Canvas`, because ttk cannot round a corner or blend a shadow into the photograph behind it. `build_screen`/`build_hero` draw the masthead straight onto the backdrop as canvas items, which is the only way in Tk to put type over an image. ttk survives only as the holding screen's Progressbar. The window is fixed at `t.WIDTH` x `t.HEIGHT` and every screen is laid out on the twelve-column grid at exactly that size, so anything added has to fit rather than scroll.
- Artwork is decoration and every load is guarded by `.exists()`: the app must still run with `assets/` gone, and the tests prove it. `build_hero` carries the Polar Bear logo at the left and the cut-out equipment photograph (`assets/equipment.png`, RGBA, scaled by height so a replacement of any shape is not squashed) in the top-right corner. It is drawn before the cards, so its height is capped to clear them at `CARDS_Y` — a taller one would simply be painted over.

# Hardware & MODBUS notes
- The Polar Bear rig is a single Eurotherm nanodac controller, `pb1`, MODBUS TCP on port 502. `functions/connect_controllers.py` opens one persistent `ModbusTcpClient` per controller at startup and still supports several; the valve rig used two (nanodac1, nanodac2).
- Every read/write MUST pass `device_id=255` (see `UNIT_ID` in `functions/read_register.py`, reused by `write_register.py`). Without it the nanodacs accept the TCP connection but never reply — this is not a gateway setup, 255 is just the unit ID iTools itself uses. Confirmed via hours of debugging; don't reintroduce the pymodbus default of 1.
- **On the valve rig's nanodacs** (not on `pb1` — see below), registers are plain signed 16-bit integers (`DATATYPE.INT16`, `count=1`) — NOT 32-bit floats. Values arrive raw and unscaled; anything with a decimal place is a fixed-point integer that must be divided by a per-channel scale factor. INT16 wraps negative above 32767, so a channel's scale must leave headroom for its full range.
- Register entries in `settings.json` are lists whose first two elements are always `[controller, address]`; `read_register`/`write_register` slice `[:2]` off the front, so extra trailing metadata (scale, unit) can be carried per channel without touching them.
- **The Polar Bear is not a nanodac.** It is similar equipment but configured very differently, so nothing learned about register blocks or datatypes on the valve rig's nanodacs carries over to `pb1`. Do not infer `pb1`'s datatypes from the `33xxx`/`43874` address ranges.
- `PlateTemp` (`pb1/33280`) is read as **FLOAT32** — `read_register(..., float=True)`, which already reads `count=2` and converts. Flagged by the user as assumed, not confirmed. `HeaterUtil` (`pb1/43874`) is **also read as FLOAT32**, and is configured to output 0-100 as a straight percentage of `HeaterPower`. Its datatype was confirmed against the live rig on 2026-08-27, correcting an earlier INT16 guess — the first datatype on `pb1` established by observation rather than inference, so do not weaken it back to an assumption. `MasterTemp` (`pb1/33296`, the sample probe) is read as FLOAT32 too, confirmed reading correctly on the rig on 2026-09-01. No `pb1` channel needs a scale factor, and all three span two registers; the INT16 note above applies to the valve rig's nanodacs, not to `pb1`.

# Program behaviour
- `main.py` polls `programmer/UserInput` every 200 ms and dispatches on its value via the `FUNCTIONS` dict. `2` terminates the program. A dispatched function returns to the poll loop when it finishes, so a session can hold several runs. Any unmapped value falls through to `keep_alive`, which reads one register per controller so idle TCP connections aren't dropped.
- Latching is achieved by the dispatched function itself looping while `UserInput` still holds its trigger value and returning once it changes — not by a flag in `main.py`. A function that returns while its trigger is still set would be re-entered immediately.
- The whole poll cycle is wrapped in a bare `except` that prints and continues, so a transient MODBUS fault never kills a running session.
- Results go to one CSV per *function call*: `main.py` calls `resolve_save_path` again for every dispatch, so a second run in the same session gets its own folder and cannot overwrite the first. `save_csv` appends a raw row as each sample lands, writing the header only if the file is new; once the operator has picked the zones, `rewrite_csv` replaces that same file in full (via a temp file and `os.replace`, so it is atomic) with the derived `Q_relative`, `Plate temperature change`, `Energy` and `Zone` columns added. One file per run, deliberately — a split raw/derived pair was considered and rejected as confusing. `main.py` opens its session log on `resolve_results_root` instead, so sitting waiting for User Value 1 never creates an empty run folder; one log covers the whole session.
- **One folder per run.** `resolve_save_path(settings, name="")` resolves the results root (`resolve_results_root`, which is the `SavePath` logic on its own), creates `<root>/<stem>/` and returns `<stem>.csv` inside it — so a run's CSV, PNG, PDF, JSON, TYP and console log all sit together under a folder named after the experiment. The stem is the operator's typed name when there is one, put through `safe_name` (strips what Windows will not take in a folder name, collapses the whitespace that leaves, caps the length, and returns `""` when nothing usable survives); with no name, or an unusable one, it falls back to the `FileName` pattern exactly as before. It will not return a folder that already exists: a repeated experiment name, or two runs inside one second (possible if `TIME_STEP_S` is lowered), takes the next number from `next_sequential_name`, which gained a `suffix` argument so it can count folders (`""`) as well as files (`.csv`).
- `choose_results_file` must use `resolve_results_root`, not `resolve_save_path`, for the file dialog's `initialdir` — the latter would create a run folder every time the operator merely opened the dialog.
- `Elapsed (min)` is minutes since the run's first sample — per run, not per session. `record_samples` captures its own `start = time.monotonic()`; nothing is passed in from `main.py`, whose dispatch signature is `func(clients, settings, save_path)`.
- `functions/start_console_log.py` mirrors all stdout/stderr for the session to `<results folder>/logs/<timestamp>.log` by swapping `sys.stdout`/`sys.stderr` for a tee object; `functions/stop_console_log.py` restores the originals and closes the file. The log file is opened **line buffered** (`buffering=1`): under Python's default block buffering a whole session sat in memory until close, so any death that skipped `stop_console_log` — the window's X, `taskkill /F`, a power cut — left a 0-byte log. Line buffering pushes each line to the OS, which survives process-level death; only OS-level death could still lose it, and that would need an `fsync` per line. It takes the **folder** the `logs/` directory goes under, not a file: `main.py` passes the results root, because a testing session spans many runs and cannot live in any one run's folder, while `force_run.py` and `reanalyse.py` pass the run's own folder so its log travels with its results. Started as soon as that folder is known and stopped at the very end of the entry point, so it misses only the "Loading settings..." print at the top.
- `pyproject.toml` needs `package-mode = false` (this is a script project, not a packaged library) — plain `poetry install` fails otherwise. Requires Python >=3.13.

# Calorimetry
- The one function this project exists to provide (README function `1`). It estimates the energy added or removed by a source/sink placed on the Polar Bear's plate, by conservation of energy.
- `pb_cooling_capacity.csv` is **not** a table of watts. Its columns are `Plate Temperature, C` and `Heating Output, %` — a steady-state calibration sweep taken with no load on the plate. At each row the machine is at equilibrium, so the heater output recorded there is exactly the cooling power the machine is producing at that plate temperature. Cooling power in watts is therefore recovered as `Q_cool(T) = HeaterPower * util_curve(T) / 100`, with `HeaterPower` (193 W) from `settings.json`.
- The file has a UTF-8 BOM (read with `encoding="utf-8-sig"`) and CRLF line endings; headers are quoted (`"Plate Temperature C"`, `"Heating Output %"`). Parse with the `csv` module and `newline=""`.
- Rows are ordered by heating output, not temperature, and the cold end is non-monotonic in temperature (-45.89, -46.51, -43.88, ...). Sort by temperature before interpolating.
- The measurement then samples every time step:
  - `Q_cool = HeaterPower * interp(T_plate, curve) / 100` — cooling power at the current plate temperature.
  - `Q_abs = Q_cool - HeaterPower * util_actual / 100`, i.e. `HeaterPower * (util_curve(T_plate) - util_actual) / 100`. The physical meaning: the gap between the heater output the machine *would* need to hold this plate temperature unloaded, and what it is *actually* using, is the heat the external source is supplying. Positive `Q_relative` = energy being added to the plate.
  - `Q_relative = Q_abs - Q_baseline`, where `Q_baseline` is the **mean** `Q_abs` over a baseline zone the operator draws by hand once the run has finished — there is no fixed baselining period any more. There is roughly sinusoidal noise on the power reading with a 90-120 s period, so a baseline taken over anything but whole cycles sits off-centre in that swing and biases every sample by the same amount. Letting the operator cut the zone by eye against the plotted `Q_abs` is what makes whole cycles selectable; `summarise_window` computes the zone's `sd` and `spread` so the choice can be judged rather than guessed, and `check_baseline` warns above `SPREAD_WARN_W` (5 W).
- **Why `Q_abs` is ~0 at an unloaded baseline** (this confused the author once; it is not a claim that cooling stops). Both terms of `Q_abs` are large and nonzero at baseline — holding, say, 25 C needs real heater input against real cooling. They are also *equal*, because that is what equilibrium means and exactly what the calibration sweep recorded. Their difference is what goes to zero. `Q_abs` is a net heat balance on the plate, not an absolute cooling power, despite the name: it is the rate at which the plate is gaining heat from everything that is not the machine's own heater and cooler.
- `Q_baseline` is therefore a residual, capturing how far the machine has drifted from its calibration sweep (ambient temperature, condenser fouling, refrigerant charge, interpolation error). Subtracting it cancels that offset at the operating point, so `Q_relative` measures the change caused by the source regardless of how stale the curve is. It is printed once the zones are chosen, not at run start; beyond roughly +/-10 W (about 5 percentage points of heater output) the curve probably no longer describes the machine and it wants recalibrating — an advisory, not a hard limit.
- Baseline subtraction cancels the offset **inside the baseline zone**, not drift between that zone and the experiment zone. If ambient temperature moves between them, `Q_cool` shifts and the change is misattributed to the source. Picking the two zones close together limits this; picking a baseline far from the experiment maximises it. On long runs this is the dominant error, and it integrates: a 2 W drift over 30 minutes is 3.6 kJ of phantom energy. Keep runs short, or ambient stable, or both.
  - `E_t = E_{t-1} + Q_relative * t_step`.
- All Q values are watts, energy joules, `t_step` seconds. Use the *measured* interval between samples for `t_step`, not the nominal setting — a blocked MODBUS read would otherwise silently corrupt the integral.
- **Conditioning:** above about -29 C the curve is a steady ~2.4-3.2 C per %, so a 1 C temperature error costs only ~0.7 W. Below -39 C it flattens to ~0.6 C per % and goes non-monotonic, so the same error costs ~3 W and the interpolation is ill-defined. Control temperatures should be chosen in the well-conditioned region; warn the operator if the baseline lands in the cold end.
- The curve is a *steady-state* characteristic, so instantaneous `Q_relative` is only valid at thermal equilibrium. During transients the plate's own thermal mass absorbs and releases energy and `Q` will overshoot; the energy integral is the robust number because those transient errors largely cancel once equilibrium returns. Report total energy as the headline figure.
- A run ends when `UserInput` leaves `1`. `select_windows` then opens a **blocking** Tk window: two panes on a shared time axis, `Q_abs` above for the baseline zone and the master probe below for the experiment zone, each with its own `SpanSelector`. Two selectors on two axes deliberately, so they cannot fight over mouse events. Both zones are pre-seeded to sensible defaults, so simply closing the window still yields a valid answer.
- `keep_alive` must keep running while that window is open or the rig drops the idle socket. `select_windows` pumps it from `figure.canvas.new_timer` (backend-agnostic, not raw Tk `after`) every `KEEP_ALIVE_MS`, wrapped so a MODBUS blip prints rather than killing the window.
- Matplotlib's backend is **no longer forced to Agg** — the selection window needs an interactive one, and matplotlib falls back to Agg by itself where there is no display. `savefig` works on either. `tests/conftest.py` forces Agg so the suite never opens a window.
- `MasterTemp` was configured by the author on 2026-09-01 as `["pb1", "33296"]`; it began as a `null` placeholder, and that path still works — with no address the column records blank and the lower selection pane falls back to plate temperature, labelled as unconfigured. Its FLOAT32 datatype was inferred from its neighbours and **confirmed against the live rig on 2026-09-01** — the probe reads correctly. Do not weaken it back to an assumption.
- `plot_work_curve` paints the figure surround `SURROUND` (`#E8E8E8`) and keeps the data area white — an explicit request from the author, not incidental styling, and `savefig` is passed the same colour because it will otherwise substitute white. The work curve's right-hand axis carries **both** temperature traces — plate and master probe, each as a change from its own mean over the baseline zone — so its label is the generic "Temperature change (C)" and its colour is neutral rather than matched to one trace. The probe trace is dropped entirely when the column is blank, rather than drawn as a flat zero. The report indicates the chosen zones: `plot_work_curve` shades both and names them in the legend, and the Typst summary carries a `baseline` and an `experiment` dict (`start_min`, `end_min`, `duration_min`, `samples`, `mean`, `sd`, `spread`). The author's template currently renders only `sd` out of that pair — `spread` reaches the operator through `check_baseline`'s console warning instead, and stays in the JSON should it ever be wanted on the page. The pre-existing top-level fields (`samples`, `duration_min`, `baseline_w`, `peak_w`, `energy_j`, `direction`, `plot`, `finished`) are unchanged, so the author's template keeps rendering; `duration_min` still means the whole recording, with the experiment's own duration under `experiment.duration_min`.
- Hardware is a **single** controller, `pb1`, with `PlateTemp`, `HeaterUtil` and `MasterTemp` alongside `UserInput` under `programmer`. `HeaterUtil` is configured to read 0-100 as a straight percentage. All three are read as FLOAT32.
